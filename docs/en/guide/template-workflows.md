# Template workflows

Project templates use `spec_version: 4` and `workflow_contract_version: 1`. Each manifest declares `provides`, `workflows` and one `default_workflow`. A service installed in an image is separate from the provider adapter operations and the calling client's protocol support. An application workflow that calls the template's HTTP server does not require a platform interpreter.

`abx template launch SOURCE --workflow application` checks the chosen workflow before building or creating resources. Run with `--yes` to authorize the billable build/create steps in noninteractive use. The provider must explicitly implement that input kind, startup mode and each required operation. `ready_cmd`, when declared, requires `exec.run`. Managed references must name their owning provider; OCI image inputs require an immutable `@sha256:` reference. An external service URL belongs to the explicit server-client path.

For a manifest with `build_profiles.portable: {dockerfile: Dockerfile.portable, context: '.'}`, select it with `--build-profile portable`. The original Dockerfile stays unchanged. The selected Dockerfile must name a usable base image or the supported official native base recipe; unknown placeholders fail before resources are created. The CLI snapshots the eligible source files and selected build profile, and checks the frozen source before preparing it. The effective base and server-wheel preparation are included in the snapshot digest; see [launch a template](template-launch.md) for the default recipe. Secret environment files are excluded. Symlink sources are rejected.

The selected adapter supplies the application endpoint for the exact sandbox and port. Requests retain proxy prefixes and signed query parameters, keep application and gateway credentials separate, and refuse redirects and anonymous retry. Application commands use this HTTP transport independently from shell or envd connectivity. Before listing or submitting commands, the CLI checks `/capabilities` on that same binding: `api_version` must be exactly `2`, and the selected endpoint must be explicitly enabled and allowed for the current identity. Malformed discovery or command catalogs fail closed; a successful HTTP response alone does not establish protocol support. A launch also checks its selected operation before retaining the sandbox.

Interpreter calls use exact operation identifiers. `code.execute` creates and deletes a temporary context; `code.default-context.execute` explicitly selects persistent default state. Named context operations require their own declarations. An interpreter 404 remains an interpreter error. It never executes the request in a shell.

Build, publication, template registration and sandbox creation record intent before submitting requests. Each journal write syncs the temporary file and containing directory; filesystems that cannot establish this durability reject the launch before resource mutation. A failed or timed-out request can leave an uncertain outcome: inspect the reported resource journal and reconcile its correlation key before retrying. The native sandbox ID is captured before session authentication or capability binding. If recording that known ID fails, cleanup is still attempted; the error reports the owned ID and any unresolved cleanup instead of treating it as an unknown create. Cleanup only targets resources owned by this launch. Retained or manually removable images and templates are recorded separately from confirmed sandbox deletion.

The directory's static compatibility result is distinct from live environment readiness and independently verified evidence. Historical receipts do not certify a new source, provider or consumer revision. Provider maturity such as Beta is independent from workflow implementation.

The built-in Express adapter supports source and managed workflows. Source launch reuses the native build/register path, records image and template ownership before submission, waits for readiness and creates from the exact returned template ID. The application starts once after sandbox creation, with its runtime environment. Native `<region>` and `<tag>` placeholders are resolved in the execution snapshot using the configured region and existing base-image defaults; the original source is unchanged. Other placeholders remain errors. Select an author-declared alternative with `--build-profile`; Express does not silently choose a portable Dockerfile. Docker builds require a working Docker daemon, ACR namespace and Alibaba Cloud AccessKeys, plus the Sandbox API key for creation. Explicit `build.mode: steps` projects use platform steps without Docker. The source-preparation operation is a CLI feature; the Python provider declaration does not claim it. Images and templates retained by a launch are listed in its recovery journal for explicit cleanup.

A `service-token` binding requires `ABX_SERVER_TOKEN` before any build or create. Missing credentials fail locally before billing starts. Successful command replies must contain an explicit `result` (including `null`); malformed replies fail instead of reporting success, and raw response bodies are not copied into error messages. Each launch checks only its selected operation: `commands.run` does not require command-list permission, and a `health` workflow uses the health endpoint.
